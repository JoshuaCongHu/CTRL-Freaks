\section{Bronze Layer}
The Bronze layer is an exact copy of the data. The same two City of Buffalo 311 files used in Phase 1 are used here \cite{data1}, \cite{data2}. Both CSV files are downloaded once into a Databricks Volume by the notebook and accessed by everyone. Since the newer file adds new records every day, taking a snapshot of it (Nov 19, 2026) ensures that all four notebooks process the same data. See Table \ref{tab:source} for both files.

Both files are processed using Spark without changing any columns to numerical types. In Spark, automatic detection of column types may result in some alterations in the data. For instance, a case number like 00990977 may lose zeros. The only changes are made to column names (to avoid spaces in Delta; Open Date is renamed to OpenDate) and two custom columns: \texttt{sourceFile} and \texttt{ingestedAt}. This is the reason why the tables in the figure below have 36 and 30 columns instead of 34 and 28. Both files are stored as separate Delta tables: \texttt{bronze\_311\_old} and \texttt{bronze\_311\_new}. They have not been merged yet because of different column names.

\subsection{Malformed records}
There are no deletions in Bronze. The major challenge here is the status description field, which contains commas, quotations and line breaks in its string value. With default Spark configurations, this would result in splitting one request into multiple corrupted rows, so we activated the multiLine and escape flags. In such a configuration, every request is considered as one row.

No other inconsistencies were reported and stored in the dataset. The proper format of all open dates is checked using the \texttt{try\_to\_timestamp} function that returns null if there is an error. There are 0 invalid and 0 missing open dates in both datasets. In addition, there are 0 missing and 0 duplicate case IDs. Missing data and the unknown string are checked for each column in the notebook, but they are not removed from Bronze as this is done in the Silver layer.

\section{Silver Layer}
The Silver layer cleans the two Bronze tables into one table called \texttt{silver\_311}. This time we employed the same 8 cleaning procedures, which were performed in Phase 1 and Phase 2 and translated them to the use of Spark DataFrames. None of them is translated to pandas. The adherence to the same rules means that Phase 3 models are trained on the same number of rows as Phase 2 models. Table \ref{tab:rules} describes each procedure with the reason for its need and what was accomplished by this procedure.

\subsection{Quality checks}
Prior to saving, the notebook runs several tests on the data set and terminates the program in the event that any of the tests fail. All the tests were successful. These tests include absence of negative latitudes, all coordinates within Buffalo, absence of the words ``UNKNOWN'' and ``NULL'', existence of council district in all records, timestamping of both dates and case ID uniqueness in all records.

We also ran the Phase 2 pandas cleaning code on the same data snapshot and compared the output to the Spark cleaning. The number of records remained the same throughout the process and was 533,940 rows.

\section{Challenge: NULL Text}
The first attempt of using Silver resulted in 533,939 rows; that is one row more than the pandas version. The cause of this difference is some address cells in the old dataset which contains the word NULL. This word is recognized by pandas as missing data, but by Spark, it is normal text data. For this reason, Spark identified this NULL address as real data and matched an additional one row to be the same-day duplicate. We added NULL as a placeholder in Operation 6, and then the row numbers matched.
